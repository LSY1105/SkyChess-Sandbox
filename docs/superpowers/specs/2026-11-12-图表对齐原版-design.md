## 1. 目标与非目标

**目标**：让沙盘的 4 张图表/报表**按官方语义**呈现，使学员能读出官方文档承诺的决策信息：
① 需求图能读出「目的地需求曲线」与「枢纽高峰时段」，② 票价矩阵能实时跟踪对手票价，③ 小结页给出官方 6 项 KPI，④ 甘特图与官方 DAILY SCHEDULE 同构。

**非目标（明确不做）**：
- 不做整体浅色主题改造（项目已记录为"已知且已记录的差异"，unslop 暗色石墨规范）。
- 不做 Summary 桑基图（官方 19 项界面清单中**没有**它；仅原版截图存在 → 降级为后续可选项）。
- 不做纯表格页的单元格级对齐（FLIGHTS / FUEL / INVESTMENTS / ROUTE METRICS / ECONOMICS）。
- 不改"回程由学员自设"的机制（与官方 Role Guide p3「回程自动计算」冲突，但属机制非图表，另案核查）。

## 2. 沙盘的教学目标（判断"该不该补"的基准）

Role Guide v3 给出 7 个岗位，图表是**岗位工具**而非装饰：

| 官方界面 | 官方原文用途 | 主用岗位 |
|---|---|---|
| 19 航线需求 | "每家航司每条航线**日航班数**（从枢纽起飞）。本航司**每个航班客座率可见**。**用此图可以选择当前及/新增航班从枢纽出发的最佳离港时刻。**曲线**红色部分显示一天中需求如何变化**。曲线**绿色部分显示枢纽机场的高峰时刻**。请注意：枢纽机场的高峰时刻**不一定与飞往航线目的地点的需求峰值吻合**。" | 排班 + 竞对分析 |
| 3 票价管理（含"网格"） | Role Guide p11："可以在界面选择票价管理的'**网格**'选项**实时跟踪竞争对手的票价决策**" | 竞对分析 |
| 13 小结 | 平均客座率、**盈亏平衡客座率**、服务质量指数、经营利润率、经营总成本、期末现金 | 全队 |
| 18 航班 | 我方逐航班 LF ＋ 对手**平均** LF 与票价 | 竞对分析 |

配套机制（Role Guide p4）：一天按**每 15 分钟一个时刻**划分；**每个目的地一个时刻只能被一个航班占用**；**曲线下方区域表示始发地需求**；**"在'绿色'时段安排起飞需要更高的成本当然也有更高的收益"** → 绿时段是第三层定价杠杆（速查卡：商务舱 / 超经济舱 / 枢纽高峰时段）。

**结论：图必须与引擎已有的机制对齐**——沙盘 `game.js:1262-1278` 已实现"把班次放在高峰时刻能多接客"（`slotPool = marketDaily × wUsed[h]`），`MARKETS[].dayShape` 给出**每市场不同**的需求形状，`GM.fareBandPeakHours` 给出**枢纽高峰**。当前图把"绿"画成"需求下降段"，学员读不出官方承诺的高峰信息。

## 3. 口径裁定（U1–U5）

| # | 议题 | 裁定 | 依据 |
|---|---|---|---|
| **U1** | "绿"怎么画 | **同一条需求曲线按"是否落在枢纽高峰时段"分两段染**：落在峰时段 = 绿，其余 = 红；**另加峰时段背景底纹** | 官方两处措辞均指"曲线…的绿色时段"；改动最小（只换分段依据） |
| **U2** | "枢纽高峰"取值 | 用**全局** `GM.fareBandPeakHours`；学员按航线覆盖的 `fareBands[].peakHours` **只影响定价、不影响画图** | 官方是"全枢纽一个高峰"（与目的地无关） |
| **U3** | 全局盈亏平衡客座率 | 按 **ASK 加权**聚合引擎既有逐航线 BE LF：`Σ(ASK_i × BE_LF_i) / ΣASK_i`；逐航线 BE LF 沿用引擎口径 `perFlightOpsCost(bh, fuelPrice) / (seats × fare)` | 速查卡 §13 公式 ＋ 引擎 `fleetEconomicsBrief` 既有口径（不另立新口径） |
| **U4** | 票价矩阵空列 | **保留全部市场列**，无报价显示"—"并 tooltip"未开通" | 原版 7 列多数为空但列头保留 |
| **U5** | 矩阵航司显示名 | 用沙盘席位名（CA 首都 / AB 弹道 / VA 愿景），表头标注对应原版名 | 小组端视角优先 |

## 4. 范围内差距项与设计

### 4.1 M-1 需求图的「枢纽高峰（绿）」语义 —— 完全缺失

- **现状**：`reports.js:765-771` 的 `segColor()` 按**涨跌**分段着色（红涨绿跌），与官方、项目速查卡 §四均冲突。
- **设计**：分段依据由"涨跌"改为"是否落在峰时段"：
  - 峰判定：`GM.fareBandPeakHours`（形如 `[[8,11],[16,19]]`）→ 小时 `h` 满足 `a <= h < b` 即为峰时段。
  - 红线 = 该市场 `MARKETS[code].dayShape`（缺省 `GM.dayShape`）按 24→68 点（15 分钟）插值后的**日需求曲线**；落峰时段段染绿，其余染红。
  - 峰时段加浅色背景底纹（`#2b3036` 级 8% 不透明度），使"高峰窗口"一眼可见。
  - 图例改写为官方语义：`— 目的地需求曲线（红=非枢纽高峰时段，绿=枢纽高峰时段）`。
- **同时提供教学钩子**：绿段 hover 显示"该时刻为枢纽高峰：峰时运价 ×{GM.fareBandPeak}"，与分时定价联动。

### 4.2 M-2 需求图的「每家航司每条航线的日航班数」柱 —— 完全缺失

- **现状**：柱 = 运力座位数，且按**整点**聚合（`reports.js:727-728` 用 `parseInt(hh)`）。
- **设计**：柱改为**每家航司该航线的每日班次**（`g.schedules` 中该航司该航线的班次数），X 位置取该班次的起飞时刻（15 分钟粒度，用 `detail[code].flights[i].departureMin` 的 `slot`），柱高 = 该班次座位容量；颜色按席位（沿用现有 `SEAT_COLOR`）。
- **"本航司每个航班客座率可见"**：柱 hover 显示该班次 `单日载客 = flights[i].served / DAYS_PER_QUARTER` 与 `LF = 单日载客 / 座位`。

### 4.3 P-1 / P-2 需求图红线口径与标题口径 —— 部分实现

- **P-1 红线**：改为该市场自己的 `dayShape` 曲线（**每市场不同**，天然解释"目的地峰值 ≠ 枢纽高峰"）。现实现的 `E.demand(...) / 90 × shape` 换成"结算同源"的口径：`marketDaily × wUsed[h]`，其中 `marketDaily = 该市场日需求总量`、`wUsed[h] = dayShape 归一化权重`。
  - **引擎一致交叉验证**：同一班次落在某时刻时，图上红线高度对应的需求池应与 `game.js:1265` 的 `slotPool` 同源（见 §6 验收）。
- **P-2 标题**：改为官方格式 `Flight Capacity and Actual Loads - (N passengers carried)`，其中 **N = 该市场每日承运总量** = `Σ_i (detail[code].flights[i].served / DAYS_PER_QUARTER)`。
  - 自洽性：N ≤ 该市场日需求总量（总量保护），N = 0 时显示 `(0 passengers carried)`（与原版 LEWIS 图一致）。

### 4.4 D-1 ~ D-3 需求图版式对齐 —— 数据或样式不一致

| 项 | 现状 | 目标 |
|---|---|---|
| D-1 Y 轴文案 | `Capacity per aircraft seats` | `Capacity and actual loads` |
| D-2 页头 | 中文说明行 | `FLIGHTS & DEMAND CHARTS` 标题条 + 金色规则线（复用 `--acc`），中文说明降级为图例行 |
| D-3 图例/数据点 | 图例含"■CA/■AB/■VA 运力"与逐点圆点 | 图例只保留官方语义两条；圆点半径 2.6 → 1.6（悬停 `<title>` 不变） |
| （新）Y 轴刻度 | `yMax × i/4` 不取整 | `yMax = ceil(max/20)*20`，主刻度步长 20，主网格 + 次网格（每 10） |
| （新）X 轴刻度 | 每 2 小时、从 04:00 起 | **06:00–23:00 逐时**，与柱位对齐 |
| （新）市场名 | 只在图上方 | 图上方 + 图下方各一条（原版两处同名小标题） |

### 4.5 M-3 Reports 增设「航线需求」页签 —— 完全缺失

- **现状**：需求图在小组端排班卡内（`player.html:222-225`）与裁判端独立页签（`teacher.html:1312`），`reports.js` 的 `TABS`（66-75）无此项。
- **设计**：`TABS` 增 `['Route Demand','航线需求']`，分支调用**已导出的** `renderRouteDemand(root, games, opts)`（同源函数，不复制实现）。
  - 约束：`reports.js` 内部只引用本模块导出（§10 坑②）。
  - 小组端排班卡内的需求图**保留**（投影时无需切页），两处由同一函数渲染。

### 4.6 M-4 Summary 6 张 KPI 卡片 —— 完全缺失

- **官方 6 项**：Average Load Factor / Break-even Load Factor / Quality Service Indicator / Margin / Total Operating Cost / Closing Cash。
- **现状**：`reports.js:216-227 summary()` 是 15 行两列表格；其中 Break-even LF **报表层完全没有**。
- **设计**：
  - 引擎：`computeTurn` 的 report 增加 `breakEvenLF`（全局，按 U3 的 ASK 加权）与 `routeBE`（每航线 `{code, beLF, ask}`）。
  - 前端：`summary()` 顶部渲染 2×3 卡片网格（复用 `el()`、`money()/pct()/num()`；金色描边复用 `--acc`；图标用内联 SVG 占位，守住零依赖）。
  - 缺值显示 `—`（无排班时 BE LF 为 null，不得显示 0）。

### 4.7 P-3 FARE MATRIX 改「网格」形态 —— 部分实现

- **现状**：`reports.js:360-372 fareMatrix()` 输出"时刻 × 航线"表头 + 每格"N班×N座"（本质是排班概览）。
- **目标**：官方"网格" = **列=市场**，列内纵向堆叠**各航司报价**（航司名 + 加粗价格），供竞对分析岗实时跟价。
- **数据源**：我方 `g.routes[].fare`；他家 `server.mjs:371` 已下发的 `peerFares`（**后端无需改动**）。
- **列**：全部市场（U4）；空列 `—` + tooltip"未开通"；航司名用沙盘席位名（U5）。

### 4.8 P-4 甘特图 3 处细节 —— 部分实现

| 项 | 现状 | 目标 |
|---|---|---|
| X 轴起点 | `T0 = 6*60`（06:00 起） | **07:00 起**（原版 Live Schedules 07:00–23:00）；若沙盘存在 06:00 班次 → X 坐标 clamp 到左边界（不丢数据） |
| 竖网格线 | 无 | 每小时一条（与刻度文字同循环） |
| 选中态 | 无 | 点击航班块 → 黑色描边（再次点击取消）；不影响既有悬停详情 |

## 5. 数据流与引擎改动

```
数据源（全部已存在，无需新建模型）
  MARKETS[].dayShape / GM.dayShape      → 红线形状（每市场不同）
  GM.fareBandPeakHours                   → 枢纽高峰时段（U2 全局）
  g.schedules                            → 每家航司该航线的每日班次与起飞时刻
  g.lastDetail / g.history[i].detail    → 每班次季度承运量（served）→ 单日载客 = served / 90
  g.routes[].fare + server peerFares     → 票价网格
  结算 slotPool（game.js:1265）          → 红线的需求池同源校验基准

引擎唯一改动
  game.js computeTurn() 的 report 增加：
    breakEvenLF : number|null            全局（U3 ASK 加权）
    routeBE     : [{code,beLF,ask}]      每航线（KPI tooltip / 明细）
  口径与既有 fleetEconomicsBrief 一致（perFlightOpsCost(bh,fuelPrice) / (seats×fare)）

前端改动（全部在 sandbox/reports.js，除注明外）
  renderRouteDemand()  ← 4.1 / 4.2 / 4.3 / 4.4（本轮最大改动，函数内改，不拆文件）
  summary() + kpiCards()  ← 4.6
  fareMatrix()        ← 4.7
  renderGantt()       ← 4.8
  TABS + 分支          ← 4.5
  player.html / teacher.html 仅改标题文案（4.4 D-2）
```

## 6. 验收标准

### 6.1 逐项可核对

| # | 验收标准（可对着截图与引擎数值核对） |
|---|---|
| M-1 | 任一航线图上，**绿段恰好覆盖 `GM.fareBandPeakHours` 区间**；峰时段有背景底纹；图例文字为"红=非枢纽高峰时段，绿=枢纽高峰时段" |
| M-2 | 同一时刻可同时看到**多家航司**的柱（按席位配色）；柱 X 位 = 该班次起飞时刻（15 分钟粒度）；hover 显示该班次 LF |
| P-1 | 两个不同市场的红线形状**不相同**（各取自己的 `dayShape`） |
| P-2 | 标题含 `(N passengers carried)`，N = 该市场每日承运总量（= Σ served / 90）；未结算时 N=0 |
| D-1~D-3 | Y 轴文案 = `Capacity and actual loads`；Y 轴刻度为 20 的整数倍且上限 ≥ 曲线峰值；X 轴 06:00–23:00 逐时；页头有金色规则线；图例仅两条 |
| M-3 | Reports 区出现「航线需求」页签，渲染与排班卡内那份**同源一致** |
| M-4 | Summary 出现 6 张卡片；Break-even LF 与 `routeBE` 一致；无排班时显示 `—` |
| P-3 | 票价矩阵按市场分列，列内含各航司报价；本组价与「运价对照」一致 |
| P-4 | 甘特图首刻度 07:00、末刻度 23:00；有每小时竖线；点块出现黑描边 |

### 6.2 引擎一致交叉验证（本轮的**核心**验收）

> 目标：图不能只是"好看"，必须**复现引擎里真实存在的机制**。

1. **形状一致性（降级为形状级断言）**：图上红线的**形状与峰值时刻**必须与引擎一致 —— 引擎 `game.js:1246-1258` 用 `dayShapeRaw(m.name)` 归一化出 `wUsed[h]`，图上须用同一 `dayShape` 归一化。
   ⚠ **不做绝对值同源**：引擎的归一化基准是"基准小时集合"（含**竞品**运营小时，图上取不到）→ 两者绝对值必然不同，只比对形状与峰值时刻。
2. **高峰收益一致性**：`game.js:1225-1272` 的"把班次放在高峰时刻能多接客"结论，必须能从需求图上**肉眼读出**（高峰处红线明显高于低谷）。
3. **BE LF 自洽**：Summary 的全局 `breakEvenLF` = `Σ(ASK_i × BE_LF_i) / ΣASK_i`，且与 `fleetEconomicsBrief` 的逐航线值一致。
4. **容量上限**：任意市场，图上标题 N（每日承运总量）≤ 该市场日需求总量。

## 8. 风险与回退

| 风险 | 缓解 |
|---|---|
| 改红线语义可能让**已按旧图做判断**的教学材料失效 | 同步更新 `项目同步文档.md` §6.4 映射表与教学包《00_真实规则_速查卡.md》引用的实现说明 |

| 需求图红线与结算口径若不同源 → 图与引擎说两话 | §6.2 的 4 条交叉验证作为**发布门**，任一不过则不合入 |

| 一次性改动面大 | 按 §4 分 8 个任务，每任务独立可验收、独立提交；任一任务失败可单独回退 |
